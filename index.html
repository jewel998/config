Developer

Emma creates a "New Checkout" flag

Thursday morning. The team built a redesigned checkout flow and wants to validate it with enterprise customers first. Emma opens the portal, creates the flag, and assigns it to the "Enterprise US + DE" segment. No code changes needed — the SDK picks it up automatically.

feature.new_checkout → trueOnly for Enterprise users in US and Germany
End User

Sarah opens the app — new checkout appears

Sarah works at Acme Corp (enterprise plan, based in New York). When her browser loads, the SDK sends her context: plan, country, tenant. The API resolves the targeting rule in 48ms and returns the result. Sarah sees the beautiful new checkout flow.

{ plan: "enterprise", country: "US" } → matchedResolved server-side. No rules exposed to the browser.
End User

Tom still sees the old checkout

Tom is on the free plan. Same app, same codebase, same deployment. But when the API evaluates his context, it doesn't match any targeting rule — so he gets the default value. Zero if/else in the code. The SDK handles the branching.

{ plan: "free", country: "US" } → not matchedDefault: false. Tom sees the standard flow.
Multi-Tenant

Different orgs, different configurations

Acme Corp (enterprise) gets AI assistant access and 500 MB uploads. StartupXYZ (pro) gets 200 MB but no AI yet. Tom's personal account gets the free tier defaults. Each tenant's SDK resolves their own config independently — full isolation between organizations.

Same flag, different values per tenantNo per-tenant deployment. Just targeting rules.
Developer

Monday: gradual rollout to Pro users

Enterprise went great over the weekend. Now Emma adds a 50% rollout for Pro users. The system uses deterministic hashing (MurmurHash3) — Priya gets it, but another Pro user doesn't. Same user always gets the same result, no session stickiness needed.

hash("new_checkout:priya_id") % 100 → 34 < 50Priya is in. Consistent across sessions and devices.

A payment edge case surfaces on Tuesday. Emma toggles the flag off in the portal. Within 2 seconds, every user's next request resolves to false. No deploy pipeline, no rollback, no hotfix branch. The old checkout is back for everyone instantly. Fix the bug, re-enable when ready.

Self-hosted

Deploy to your own Firebase in minutes

You own the infrastructure. Your data stays on your project. We provide the code — you deploy it.

1

Clone the repository

git clone https://github.com/jewel998/config && cd config

The full source — portal, SDK, cloud functions, docs. All yours.

2

Connect your Firebase project

firebase use --add your-project-id

Point it at your own Firebase. Firestore, Hosting, Cloud Functions — all on your account.

3

Deploy everything

pnpm install && firebase deploy

Portal, API, and hosting — deployed to your infrastructure in one command.

4

Install the SDK in your app

npm install @jewel998/config

Point the SDK at your deployed API. Generate an API key from your portal and start fetching flags.

Upgrades & migrations

When new versions are released, pull the latest changes and redeploy. We provide migration guides for breaking changes. Your data stays in your Firestore — always under your control.
